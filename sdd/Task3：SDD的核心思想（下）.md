# Task3：SDD的核心思想（下）

承接 Task1、Task2：前面已经认识 Vibe Coding 的危害，区分瀑布、敏捷与 SDD 的差异；本章重点掌握 SDD 标准定义，理解 SDD 并不是全新诞生，而是经历三次历史复兴，理解为什么在 AI 时代才真正迎来落地时机。

## 一、SDD 规范驱动开发

> **规范驱动开发（Specification‑Driven Development，SDD）：规范是第一手工件，代码是规范的衍生物。**  
> 工程师首要产出不是代码，而是规范制品（需求、架构、接口契约、任务清单）；规范作为项目**唯一真相来源 Single Source of Truth**，AI 或者开发者依据规范完成代码实现；当代码与规范出现冲突时，以规范为准，修正代码，而不是随意修改规范。

> 💡我的理解：  
> 传统开发圈子流行一句话：`Talk is cheap, show me the code`（少说空话，看代码）。AI 时代发生反转：**代码生成成本变得极低，写出清晰、无歧义的规范反而变成稀缺能力**。  
> 放到我的项目：过去我优先产出 Controller、Service 代码；SDD 要求，做新功能时优先产出 proposal、design 等规范文档。代码可以由 AI 生成，但业务约束、边界、取舍，必须由人写在规范里。

## 二、SDD 的三次复兴历史

SDD 不是凭空发明的新概念，历史上曾经三次兴起，前两次都没有大规模普及，直到 AI 大模型时代迎来第三次复兴。

### 第一次复兴：形式化规约、契约式设计（上世纪 80‑90 年代）

代表思想：契约式设计 DbC、形式化方法、Z 语言、VDM。

- 核心思路：在写代码前，用严谨的数学、形式语言定义系统行为、前置后置条件。
- ✅优点：逻辑严谨，系统行为可验证；多用于航空航天、军工高可靠系统。
- ❌局限：学习门槛极高，编写规范成本巨大，普通商业项目落地成本远高于写代码，难以在互联网行业普及。

### 第二次复兴：模型驱动 MDD、BDD 行为驱动开发（2000‑2010 年代）

两大分支：

1. **MDD 模型驱动开发**：使用 UML 建模，期望从模型直接生成可运行代码；
2. **BDD 行为驱动开发**：用自然语言描述业务行为，生成测试，驱动开发。

- ✅优点：降低形式化语言门槛，面向业务，把需求、行为前置。
- ❌局限：代码生成器能力有限，模型和代码经常脱节；维护模型成本高，现实项目中模型文档容易过期，慢慢被弃用。

> **在本时代后期的 API 领域，出现少有的成功实践：OpenAPI/Swagger「契约优先」思想取得大规模落地。**

### 第三次复兴：大模型 AI 时代的 SDD（2024‑2025 至今）

大模型带来根本性变化：

1. LLM 可以读懂 Markdown 等人类可读的结构化规范；
2. AI 可以直接依据规范批量生成业务代码、单元测试；
3. Vibe Coding 大规模暴露出无规范开发带来的工程债务，行业开始寻找解法。

- ✅核心改变：**编写规范依旧是人来完成，但 “规范转代码” 这件繁重工作交给 AI 承担，大幅降低落地成本**。
- 不再需要复杂数学形式语言，普通 Markdown 就可以作为规范载体。

## 三、三次复兴历史对比小结

| 阶段    | 时代        | 载体                   | 实现方式               | 普及情况                         |
| ----- | --------- | -------------------- | ------------------ | ---------------------------- |
| 第一次复兴 | 80‑90 年代  | 数学形式化规约              | 人写规范，人全部手写代码       | 仅军工航天等高可靠领域                  |
| 第二次复兴 | 2000‑2010 | UML、BDD 自然语言、OpenAPI | 人写模型 / 契约，工具有限生成代码 | BDD、OpenAPI 在部分领域落地，MDD 整体没落 |
| 第三次复兴 | 2024‑至今   | Markdown 结构化 Spec 文档 | 人写规范，AI 完成主要代码生成   | 面向普通业务项目，适合 AI 辅助开发场景        |

> 不要误解 SDD 是全新黑科技，它吸收历史几十年软件工程经验，只是 AI 补齐了最后一块短板。学习 SDD 也是在补齐自己软件工程历史认知，软考也会考软件开发方法论演进，可以互相辅助记忆。

## 四、本章思考题解答

> SDD 五大核心原则回顾：
>
> 1. **规范先行 Spec First**：先产出规范文档，后写代码；不要先编码再补文档。
> 2. **规范即文档 Spec as Doc**：规范本身就是项目文档，是可读的设计资料，不是内部草稿。
> 3. **规范可执行 Executable Spec**：规范可以用来生成代码、测试、接口契约，不止是纯文字。
> 4. **规范可版本控制 Versioned Spec**：规范文档纳入 Git 版本管理，修改历史可追溯，和代码一起提交。
> 5. **代码服务规范 Code Serves Spec**：代码是规范的实现；当代码和规范冲突，修改代码，不动规范。

### 思考题 1

> 问题：请回顾 SDD 的 5 个核心原则，若现阶段只能先执行其中一个（其余 4 个暂时无法兼顾），你会优先选择哪一个？为什么？思考哪个原则投入产出比最高。

**作答：**  
我优先选择 **规范先行（Spec First）**。

理由：投入产出比最高，是整套 SDD 工作流的入口起点。五大原则是顺序递进关系，**规范先行排在整个链路最顶端**，不做到先写规范再编码，后面 “规范可执行、版本控制、代码服务规范” 全部无从谈起。  
只要把 “规范先行” 落实：新增功能前，先写 \[design.md\](design.md) 设计文档，再动手写代码，就可以直接遏制 Vibe Coding 即兴编码的问题。

### 思考题 2

> 问题：本章展示了 \[proposal.md\](proposal.md)、\[design.md\](design.md)、\[tasks.md\](tasks.md) 三种规范文档。若项目时间有限，仅允许你撰写其中一种，你会选择哪一种？理由是什么？该选择可能因项目类型不同而有所差异，如独立开发与团队协作、开发新项目与维护遗留项目，其侧重点往往各不相同。

**作答：**  
个人开发者做独立新项目，优先选择 **`design.md`\*\*\*\*（设计文档）**。

理由：

1. 三份文档定位区分

- `proposal.md`：偏向提案，回答**要不要做**，聚焦价值、目标、风险，偏向立项；
- `design.md`：偏向方案，回答**怎么做**，包含模块划分、数据库设计、接口契约、边界约束；
- `tasks.md`：偏向拆解，回答**做什么、按什么顺序做**，任务拆分清单。

1. 独立开发新项目场景，\[design.md\](design.md) 承上启下价值最大。  
   proposal 更多用来论证 “该不该开发这个功能”，个人项目中立项决策可以在脑中完成；tasks 只是把设计拆成任务，如果设计本身模糊，拆分出来的任务也是无效。  
   \[design.md\](design.md) 直接定义模块边界、表结构、接口，这正是写代码之前最核心的信息。只要设计文档写清楚，我既可以自己编码，也可以交给 AI 生成代码，后续也可以由 design 快速导出 tasks 任务清单。
2. 不同项目场景的差异化选择：

- 团队协作新项目：优先`proposal.md`，对齐所有人对需求、目标的认知，避免理解偏差；
- 维护遗留老项目：优先`tasks.md`，基于现有系统拆解迭代任务，不需要大规模重写设计；
- 个人快速迭代原型：优先`design.md`，和我当前场景一致。

### 思考题 3

> 问题：SDD 的第二春（OpenAPI 时代）和第三春（AI 时代）之间，最大的区别在于规范格式：YAML 与 Markdown 的对比。使用结构化但非形式化的 Markdown 格式撰写规范，究竟具备哪些优势，又可能引入哪些风险？如果 AI 的自然语言理解能力持续提升，这一选择是否会随之改变？

**作答：**  
OpenAPI 时代主流是 YAML，属于强结构化机器可读；AI 时代 SDD 更偏向 Markdown，结构化，但非严格形式化。

#### Markdown 规范的优势

1. **对人极度友好**：可以自由加入业务背景、权衡取舍、注释说明。YAML 适合机器解析，但可读性差，很难写大段业务说明。人在写规范的时候，不仅仅定义字段，还要记录为什么这么设计、排除了哪些方案，这部分内容 YAML 很难承载。
2. **门槛低上手快**，普通开发者无需学习复杂 YAML 语法，直接写 Markdown，适合个人自学、快速迭代，GitHub 原生完美支持渲染。
3. **大模型天然擅长理解 Markdown**，既可以阅读表格、标题、列表这类结构化信息，又能读懂自然语言业务逻辑，非常适配 AI 辅助编码的工作流。

#### Markdown 带来的风险

1. **没有强制语法校验**。YAML 有工具可以校验格式正确性，Markdown 是非形式化，全靠人自觉。会出现写出来的规范结构混乱、信息缺失，不同人写的 Markdown 格式千差万别，没有统一约束。
2. **机器无法自动校验规范与代码一致性**。OpenAPI (YAML) 可以做接口校验、自动生成 SDK；Markdown 文档无法被工具直接解析校验，需要人或者 AI 人工去比对代码和文档是否冲突。
3. 容易写的过于冗长散漫，变成流水账，失去规范的严谨性。

#### AI 能力持续提升后的判断

不会完全抛弃 Markdown，但会走向两者结合，而不是完全替换。

- 当 AI 自然语言理解持续变强，Markdown “人写自然语言规范” 的优势会进一步放大；但是机器自动校验、契约校验的能力，依然需要 YAML/JSON 这类强结构化格式。
- 未来更合理模式：**人使用 Markdown 编写高层业务规范、设计思路；AI 自动从 Markdown 提取信息，输出 OpenAPI (YAML) 这类机器可校验契约文件**。二者互补，不会单一格式完全取代另一方。
