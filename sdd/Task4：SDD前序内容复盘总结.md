# Task4：SDD前序内容复盘总结

承接 Task1‑Task3 全部学习内容，整体复盘、落地规划。

## 一、学习内容整体回顾（Task1~Task3 核心要点梳理）

### Task1：Vibe Coding 的甜蜜与陷阱

认识了**Vibe Coding（氛围感编码）**：依靠自然语言对话让 AI 生成代码，决策全部保存在聊天会话，缺少正式工程制品沉淀。

- 五大问题：**需求蒸发、上下文漂移、不可审查、不可复现、不可维护**，项目规模上涨后技术债务持续放大。
- 对比瀑布、敏捷、Vibe Coding、SDD 四种开发模式。
- SDD 六阶段工作流，区分**规范层（人产出 \[proposal.md/design.md/api\](proposal.md/design.md/api)‑spec.yaml/\[tasks.md\](tasks.md)）与代码层（AI 实现）**。
- 思考题认知：AI 写 CRUD 代码门槛极低，**定义规范、拆解需求的能力才是开发者的核心竞争力**。

### Task2：按图索骥：SDD 的核心思想

揭示 AI 辅助项目为什么容易烂尾：Vibe Coding 的缺陷随规模放大。

- 复盘瀑布、敏捷、Vibe Coding 三者的优缺点；厘清关键误区：**SDD≠复古瀑布模型**。
- 瀑布：文档一次性冻结，变更成本极高；
- SDD：**规范与代码一起迭代，规范纳入 Git 版本管理，是活的契约文档**。
- 重新解读敏捷宣言：敏捷拒绝的是**过时静态归档文档**，不是拒绝规范；轻文档不等于零文档。

### Task3：SDD 的核心思想

SDD 不是全新发明，经历三次历史复兴，AI 补齐了过去的短板才得以普及。

1. 第一次复兴：80‑90 年代形式化规约、契约式设计；严谨但门槛过高，仅高可靠领域使用。
2. 第二次复兴：2000‑2010 MDD、BDD；整体没落，仅 OpenAPI/Swagger 契约优先思想获得成功。
3. 第三次复兴：AI 大模型时代；**人写规范，AI 承担 “规范转代码” 繁重工作，落地成本大幅下降**。

SDD 五大核心原则：规范先行、规范即文档、规范可执行、规范可版本控制、代码服务规范。  
通过三道思考题理解：

- 个人项目优先落地 \\*\\* 规范先行（Spec First）\\*\\* 投入产出比最高；
- 独立新项目优先写`design.md`设计文档；
- Markdown 可读性强但缺少机器校验，未来走向 Markdown 高层描述 + YAML 契约互补。

## 二、SDD 落地的现实取舍：不追求完美，追求可执行

学习完 Task1‑3 之后，我意识到 SDD 不等于写大量厚重文档，作为个人自学项目，需要做现实取舍：

1. ✅优先落地：**规范先行、规范纳入 Git 版本管理、代码服从规范**；新增核心自研模块先写规范，再编码；
2. ⚠️对于简单演示、小工具、简单 CRUD 模块，不需要全套完整 proposal+design+tasks，适度轻量化；
3. 不用学习复杂的数学形式化规约，以 Markdown 作为主要规范载体；关键接口可以让 AI 辅助生成 OpenAPI YAML 做机器校验；
4. 规范不是写完就永久不变，需求发生变更时，优先更新 spec 文档，再修改代码，做到规范和代码同步迭代。

## 三、整体学习总结

从认识 Vibe Coding 的危害，区分瀑布、敏捷，再了解 SDD 的历史三次复兴，整套学习让我跳出 “AI 能跑通代码就万事大吉” 的认知。  
SDD 给我的最大启示：**AI 时代，编码执行的成本越来越低，人的价值集中在定义需求、划定系统边界、做技术权衡、输出可追溯的规范契约**。
